BorgBackup vs. Restic for VPS: Which One Actually Saves Your Bacon in 2026?

2026-06-18 Cloud & VPS

Choosing between BorgBackup and Restic for VPS backups in 2026 isn't a casual decision, it's the difference between a five-minute recovery and a three-day nightmare when your server goes sideways. Both tools deduplicate, encrypt, and compress your data, but they take fundamentally different approaches to storing and verifying it. I've run both in production on dozens of Linux VMs over the past five years, and the tradeoffs are more nuanced than most comparison posts suggest.

This guide breaks down the real-world differences between BorgBackup and Restic specifically for VPS workloads running on providers like Hetzner, DigitalOcean, Vultr, and OVH. We'll look at performance, security, restore speed, cloud support, and operational pain points so you can pick the right tool for your infrastructure.

BorgBackup vs. Restic: The 30-Second Summary

Both BorgBackup and Restic are open-source, client-side encrypted backup tools with deduplication, but they target slightly different use cases.

  • BorgBackup is a server-side repository model. You need SSH access to a backup target. It uses a custom, highly efficient repository format optimized for local and remote storage via SSH.
  • Restic is a cloud-native backup tool. It supports S3, SFTP, Backblaze B2, Azure, GCS, and even local disks out of the box. Its repository format is portable and works identically across all backends.

That single architectural difference drives most of the practical tradeoffs you'll encounter.

Core Architecture: How They Store Your Data

Understanding the underlying repository design is essential before you commit to either tool, because it affects restore speed, partial recovery, and how you handle repository corruption.

BorgBackup Repository Structure

Borg uses a custom segment-based repository with segment files containing packed, compressed, and encrypted chunks. It has a local cache of file indexes, which dramatically speeds up operations on large datasets once the cache is warm. The repository lives on a remote host accessed via SSH, and Borg stores everything in a directory with a specific layout including config, data, and index subdirectories.

The key advantage: Borg's index cache means subsequent backups are extremely fast, often just seconds for small daily deltas, even on multi-terabyte datasets. The downside: the cache is local, so if you lose it, the next backup requires a full reindex, which can take hours on a 5TB dataset.

Restic Repository Structure

Restic stores data in a content-addressable store (CAS) of pack files. Every chunk is identified by its SHA-256 hash, and the repository is essentially a key-value store where keys are content hashes. This makes the repository format completely portable and verifiable. Restic can always reconstruct the index by reading pack files, so there's no local cache dependency.

The tradeoff: Restic operations involve more repository round-trips, which can slow down backups to remote backends, especially over high-latency connections. However, the repository can be validated with the check command, which reads and verifies every byte.

Installation and Setup on a VPS

Both tools are available in standard package repositories and as static binaries, making installation straightforward on any modern Linux distribution.

Installing BorgBackup

On Debian/Ubuntu-based VPS images, install Borg directly from the repositories:

  • Ubuntu 24.04+ ships Borg 1.4.x in the universe repository
  • Debian 12 includes Borg 1.2.x in the main repository
  • For the latest features, use the official static binaries or pip install

The basic workflow requires you to set up an SSH key on your backup target, initialize the repository, and run your first backup. Borg requires an SSH-accessible server as the backup target, so you need either a second VPS, a dedicated backup server, or a provider that supports Borg via SSH.

Installing Restic

Restic is a single static Go binary, so installation is trivial:

  • Download the binary from GitHub releases
  • Place it in /usr/local/bin/
  • Set executable permissions

No dependencies, no daemon, no configuration files. Restic supports S3-compatible storage out of the box, which means you can point it at any S3-compatible object storage including AWS S3, Backblaze B2, Wasabi, MinIO, and Storj without setting up a separate backup server.

For VPS users without a second server: Restic wins on convenience because you don't need to manage a backup host.

Performance Comparison: Backups and Restores

Performance is where the two tools diverge most noticeably, and the differences depend heavily on your network latency, storage backend, and dataset characteristics.

Backup Speed

On warm operations (subsequent backups with a populated local cache), Borg typically outperforms Restic by 2-4x, especially for incremental backups. A 50GB VPS with daily changes of 500MB might complete a Borg incremental backup in under 30 seconds once the cache is warm, while Restic could take 1-3 minutes depending on the backend.

On cold operations (first backup or after cache loss), the gap narrows significantly. Restic's design is more I/O-bound, while Borg's segment-based design favors sequential writes.

Restore Speed

Restore speed is more complex. Borg can extract individual files extremely fast when the local cache is available, because the index tells it exactly which chunks to fetch. Without the cache, you have to rebuild the index first, which adds significant time.

Restic's restore performance is consistent regardless of whether you have local state, because the tool can always locate chunks via the repository metadata. On a 500GB dataset over a 1Gbps connection, expect Borg to restore in 45-90 minutes with a warm cache, while Restic may take 60-120 minutes depending on backend performance.

Bottom line: If your VPS has a small dataset and frequent small changes, Borg's speed advantage is significant. If you have a large dataset and infrequent restores, Restic's consistency is more valuable.

Encryption and Security

Both tools use authenticated encryption, but the implementations differ in important ways.

Borg Encryption

Borg supports AES-OCB (deprecated) and ChaCha20-Poly1305 for authenticated encryption. The repository is encrypted client-side before data leaves the VPS, so the backup server never sees plaintext data. Borg also supports append-only mode for backup targets you don't fully control.

One historical concern: Borg 1.x had a security advisory (CVE-2023-36811) related to the manifest spoofing, fixed in 1.2.5. Borg 2.0+ (released 2024) fixed the underlying repository design and is now the recommended version.

Restic Encryption

Restic uses AES-256-GCM or ChaCha20-Poly1305 with Poly1305, and the repository is always encrypted with a key derived from your repository password. Every pack file is independently encrypted, which means Restic can verify integrity on a per-pack basis without needing to decrypt the entire repository.

Restic's design philosophy prioritizes verifiability. The check command reads every pack file and verifies its hash and structure, catching corruption early. Borg's check command is less comprehensive and historically had issues with detecting partial corruption.

For paranoid workloads: Both tools are excellent. Restic's pack-level integrity verification gives it a slight edge for long-term archival where bit rot is a concern.

Storage Backend Support: Where Can You Back Up?

This is where Restic pulls ahead decisively for most VPS users.

BorgBackup Backend Support

Borg works with:

  • Local disk (via filesystem)
  • Remote SSH server (the standard approach)
  • S3 via borg-specialized forks or third-party tools
  • Not natively designed for object storage

If you want to back up to Backblaze B2 or AWS S3, you need to run Borg on an intermediary VPS that has local storage synced to S3, or use a third-party tool. This adds complexity and cost.

Restic Backend Support

Restic supports natively:

  • Local filesystem
  • SFTP (via SSH)
  • REST server (restic's own protocol)
  • Amazon S3 and S3-compatible storage (Backblaze B2, Wasabi, MinIO, Storj)
  • Microsoft Azure Blob Storage
  • Google Cloud Storage
  • Aliyun OSS
  • rclone mount as a backend (for dozens more)

For VPS users without a second server: Restic lets you back up directly to cheap object storage, often at $5-10/TB/month. Borg requires a backup server, which adds $5-20/month to your infrastructure costs.

Operational Considerations: Day-to-Day Management

The operational burden of running either tool in production is where most users form their lasting opinions.

Repository Maintenance

Borg requires periodic compaction to reclaim space from deleted archives and to merge small segments. The borg compact command is fast but must be run regularly, or your repository will fragment and performance degrades over time.

Restic handles cleanup differently. The forget command removes archives according to retention policies, and the prune command reclaims space by rewriting pack files. Pruning is more I/O-intensive than Borg's compact but results in a more uniformly organized repository.

Both tools benefit from periodic check runs to verify integrity, and both should be monitored for storage growth and repository health.

Pruning and Retention

Restic's retention policy syntax is more flexible and human-readable:

  • Keep 7 daily, 4 weekly, 6 monthly snapshots
  • Apply per-host retention independently
  • Group-based retention for related backups

Borg's retention is configured per-repository and can be applied via the borg prune command, but the syntax is less intuitive and many users find it harder to express complex retention schemes.

Real-World VPS Scenarios: My Recommendations

After running both tools in production on dozens of VPS instances, here's how I choose between them in 2026.

Choose BorgBackup If:

  • You already have a second VPS or dedicated server for backups
  • Your dataset is large (>1TB) and you make frequent small changes
  • Backup speed is critical (sub-minute incremental backups)
  • You're backing up databases or mail servers with many small files
  • You're comfortable with SSH-based repository access

Choose Restic If:

  • You want to back up directly to S3-compatible object storage
  • You manage multiple VPS instances across providers
  • Repository verifiability and corruption detection are top priorities
  • You want zero operational overhead (no backup server to maintain)
  • You need flexible retention policies and easy cloud integration

My Personal Setup

For my own infrastructure in 2026, I run Restic on all production VPS instances backing up to Backblaze B2 at $6/TB/month. The cost is predictable, the setup is identical across providers, and the repository integrity verification gives me confidence that backups will actually restore when needed. For a dedicated database server with a 4TB dataset and frequent small writes, I run BorgBackup to a colocated backup server because the warm-cache backup performance is unmatched.

Common Pitfalls and How to Avoid Them

Regardless of which tool you choose, these mistakes can ruin your day.

Not Testing Restores

Both tools have interfaces that make backups easy, but neither forces you to test restores. Schedule monthly restore drills to a separate VPS or local VM. A backup you haven't restored is a backup you don't have.

Storing the Repository Password with the Backup

If your repository password sits in /root/.borg or as an environment variable on the same VPS you're backing up, your backup is only as secure as your root access. Use a password manager, a hardware token, or split the key between operators for high-value backups.

Ignoring Repository Corruption

Both tools can develop repository corruption over years, especially on cheap storage or unreliable network connections. Run check regularly and monitor exit codes. Restic's pack-level checksums make corruption detection more reliable, but neither tool is magic, your storage layer can still fail.

Not Monitoring Backup Success

Configure your backup system to alert on failure, not just log success. A silent backup failure is worse than no backup at all, because it gives you false confidence.

The Verdict for 2026

BorgBackup and Restic are both excellent tools, and the "right" choice depends on your operational context. For most VPS users in 2026, especially those running 1-5 instances without dedicated backup infrastructure, Restic is the better default because it works with cheap object storage out of the box and requires no second server.

For users who already operate dedicated backup servers or have very large datasets with frequent small changes, BorgBackup remains the faster, more efficient choice. The performance difference is real and measurable.

Whichever tool you choose, commit to testing restores, monitoring for failures, and reviewing your retention policies quarterly. The best backup tool is the one you actually use, and both BorgBackup and Restic will absolutely save your bacon when configured correctly.

Conclusion

The BorgBackup vs. Restic debate comes down to operational philosophy, not technical superiority. Borg is a server-side repository tool that rewards investment in dedicated backup infrastructure with unmatched performance. Restic is a cloud-native tool that prioritizes portability, verifiability, and ease of deployment. For most VPS users in 2026, Restic's flexibility and zero-infrastructure setup make it the pragmatic choice, but Borg's raw performance keeps it relevant for high-throughput workloads. Pick the tool that matches your infrastructure, test your restores religiously, and you'll be fine when disaster strikes.

FAQ

Can BorgBackup back up to S3 or Backblaze B2?

Not natively. Borg requires SSH access to a backup target. To use S3-compatible storage with Borg, you need a small intermediary VPS that syncs its local Borg repository to S3 using a tool like rclone. This adds cost and complexity compared to Restic's direct S3 support.

Is Restic slower than BorgBackup?

On warm incremental backups with a populated local cache, Borg is typically 2-4x faster than Restic. On cold operations or restores, the performance gap narrows significantly. For most VPS workloads with under 1TB of data, the difference is negligible in daily operations.

Which tool is more secure?

Both use authenticated encryption (AES-GCM or ChaCha20-Poly1305) and are considered cryptographically sound. Restic has a slight edge for long-term archival because its pack-level integrity verification makes corruption detection more reliable. Both tools had security advisories in their history, so keep them updated.

Can I migrate from BorgBackup to Restic (or vice versa)?

Not directly. The repository formats are incompatible, so migration requires a full backup to the new tool, a verification, and then a decommissioning of the old repository. Plan for a transition period where you run both tools in parallel.

Do BorgBackup and Restic support Windows VPS instances?

Yes, both run on Windows. Borg has official Windows binaries, and Restic works natively on Windows via its Go binary. Performance characteristics are similar to Linux, though Windows file system semantics can affect deduplication efficiency.

What happens if my VPS is completely destroyed?

With either tool, you can restore to a fresh VPS by installing the tool, initializing a new repository (or reusing the existing one), and running the restore command. Restic has a slight edge here because you don't need to set up SSH access to a backup target first, you can restore directly from S3 to a new instance.
